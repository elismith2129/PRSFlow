# PRSFlo Architecture Audit — July 28, 2026

*Requested by Eli before the UI redo and before expanding live usage beyond the CRM. Every claim below is measured from the codebase, not remembered.*

---

## Verdict

**Do not rewrite. Rework in place, in phases.** The foundation — stack, security model, data model, realtime discipline, documentation — is sound, and materially better than most first builds. The real risk is not the architecture; it's concentrated in two places: **(1) there is no safety net** (no error monitoring, mostly-unchecked database writes, no working local dev, no tests), and **(2) the code is organized into a few giant files with duplicated logic**, which makes every change riskier and slower than it should be. Both are fixable incrementally, and the UI redo you already want is the natural vehicle for fixing the second one.

The app is ~30,750 lines of TypeScript/TSX across app/components/lib/hooks.

---

## What's genuinely good (keep, don't touch)

- **Security model.** RLS enforced on every table keyed on `user_profiles.role`, service-role API routes for privileged writes, PIN auth with server-side rate-limited verification, private storage buckets with signed URLs, per-IP rate limiting on public endpoints. This is real enterprise-grade posture for an internal tool.
- **Realtime discipline.** 24 `channel()` subscriptions opened, 24 `removeChannel` cleanups — a perfect match. The "every fetch pairs with a subscription" standing rule is actually followed.
- **Dependency hygiene.** Nine production dependencies total. No bloat, tiny attack surface, nothing exotic. (Note: the app is actually on **Next 16.2.6** — the docs still say Next 14; update them.)
- **Backups + docs.** Daily automated Drive backups; PROJECT_LOG/CLAUDE.md/Tech-Stack discipline most professional teams don't manage. This audit was only possible because of it.
- **The recent WO consolidation.** Making the Work Order the single source of truth with the booking as a projection removed the single worst structural flaw (two-form sync). The data model direction is now right.

---

## Risks, ranked

### P0 — The safety net is missing (this is the stability risk)

1. **~80% of database calls don't check for errors.** 291 `await supabase` calls; ~55 check the returned `error`; 20 `console.error`s total. A staff member hits Save, the network hiccups or RLS rejects, the failure is silently discarded, the data is gone, and nobody — not them, not you — knows. For a business system this is the #1 fix.
2. **Zero error boundaries and zero monitoring.** No `error.tsx` / `global-error.tsx` anywhere in the app router, no Sentry or equivalent. A render error = white screen with no trace. You currently discover bugs when staff complains.
3. **No working local dev, no tests, no staging.** `npm run dev` has been broken since PIN login; verification is "push → wait for deploy → click around." Combined with no tests (a deliberate, accepted decision), the feedback loop itself is the fragile part. Fixing local dev is cheap and pays for itself immediately.
4. **Multi-step saves aren't atomic.** Booking + WO + studio rows + projection are sequential client-side writes; a mid-sequence failure leaves partial state. This class of problem already produced the 299-duplicate-WO incident. 21 `.maybeSingle()` calls remain (the documented footgun from that incident). The heavy save paths (WO create, WO save+projection) belong in Postgres RPCs — one call, all-or-nothing.

### P1 — Code organization (makes everything slower and riskier)

5. **Monolith files.** `crm/page.tsx` **3,579 lines**, `WorkOrderPopup.tsx` 2,499, dashboard `page.tsx` 2,196, `calendar/page.tsx` 1,821, `BookingForm.tsx` 1,675. The top five files are ~38% of the entire app. Every feature touch lands in one of these, which is why changes feel clunky and regressions happen.
6. **Duplicated core logic, already drifting.** `fmtTime` defined in **6 files**, `timeToMins` in 4, `calcHours` in 3, `fmtMoney` in 3, `dateRange` in 3. The `calcHours` copies already disagree (one wraps overnight sessions, one returns null) — that's a live logic-drift bug class, in billing math.
7. **TypeScript can't protect you.** `strict: false`, 57 `as any` casts, `target: es5` (needlessly old). The type system is present but disarmed.

### P2 — Data-model debt (fine today, painful later)

8. **Money and dates stored as text** (`rate`, `food_amount`, `engineer_rate`… all strings), and the text/uuid mismatch on contact IDs we hit during the WO migrations. Day-to-day it works; the moment you want reporting, totals across sessions, or the QuickBooks integration, text money becomes a constant tax. Migrate when that integration gets close, not before.
9. **Dead code.** `UnifiedSessionForm.tsx` (1,066 lines, zero importers), `BookingForm.tsx` (1,675 lines, nearly unreachable post-rebuild), legacy `mic_inventory` table. Harmless but inflates every audit/search/AI-context pass. Delete in a cleanup commit once the WO rebuild fully settles.

### The UI-redo question specifically

10. **2,693 inline `style={{}}` objects; light mode is 65 CSS override rules matching inline-style substrings.** This is the pattern that forced a 728-instance mechanical sweep just to change the body font. A UI redo done the current way will fight this the whole time and produce another fragile override layer. The CSS-variable token system in `globals.css` is a good foundation — the redo should build on it with a small set of shared styled components (Button, Input, Card, Modal, Table) instead of per-element inline objects.

---

## Recommended plan (phased, each phase ships value alone)

**Phase 0 — Safety net (do first, ~1–2 sessions).**
Fix `npm run dev`. Add `app/error.tsx` + `global-error.tsx` (friendly error screen instead of white page). Add error monitoring (Sentry free tier). Add a single shared `saveOrToast()` helper that wraps Supabase writes, checks `error`, and shows the user a visible failure toast — then adopt it in the live CRM paths first.

**Phase 1 — Data integrity (~2–3 sessions).**
Create `lib/time.ts` + `lib/format.ts`; delete the 15+ duplicate helper definitions and import from one place (fixes the calcHours drift in billing math). Move WO create and WO save+projection into Postgres RPC functions for atomicity. Eliminate remaining risky `.maybeSingle()`s. Bump tsconfig to `target: es2020` and turn on `noImplicitAny` (staged path to strict).

**Phase 2 — UI redo = decomposition (ongoing, page by page).**
Do the redo you want, but make each page's redo also its refactor: extract shared UI primitives (token-based, no inline-style forests), split the monolith pages into components as they're restyled. Start with the surfaces about to go live (calendar/WO), then CRM. One page per branch, previewed, merged.

**Phase 3 — When QuickBooks nears.**
Money/date column typing migration + reporting views. Also the deferred Step 9 (retire `work_orders.booking_id`) once the runner hub is migrated to the new link.

---

*Bottom line: you built a real system with a sound skeleton and unusually good ops discipline. It does not need to be torn down. It needs a safety net, then consolidation — and the UI redo is the right excuse to do the consolidation without a dedicated "refactor project" nobody enjoys.*
