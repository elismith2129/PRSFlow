Hiring — one case per person, the checklist for it, and the two documents they sign in the app

Type a name, pick New hire · Promotion · Separation, and you get that checklist with the dates already on it. Offer letter and job description are generated from a short form, emailed, and signed on a login-free page — the signed PDF files itself against the case and ticks the box. ADP steps are on the list with the exact menu path, so nobody has to remember them. This is deliberately smaller than the HR-SPEC's template engine: three fixed lists and two documents, which is what's actually needed this week.

1The page: open cases, and starting one

Starting a case is one line. The name, the kind, and one date — the checklist dates itself from that date. Separation asks one more question first, because that question sets the pay deadline.

This is the /sign/<token> page on their phone: the letter, a name box, one checkbox, one button. No login, no PIN, no account — a new hire has none of those. We record typed name, time, IP, and the auth user if they happened to be signed in. The token dies once signed; the PDF is what remains. A typed-name signature with an intent checkbox is a valid electronic signature under E-SIGN/UETA — it's what the ADP onboarding forms do too.

lib/hrDocs.tsrenders a document's fields → HTML (for the mail and the sign page) and → PDF (same renderer stack as /api/wo-package). Templates are code with merge fields; JD body is per-title seed text.
/sign/[token]Login-free page in app/sign/ beside app/m/. Letter · name box · intent checkbox · button. Dead after signing (shows the signed copy).
/api/hr-doc-send · /api/hr-doc-signSend mints the token and mails (soft-fail like memos). Sign verifies the token, stamps the signature, renders + stores the PDF, emails a copy to the signer, ticks docs_signed on the case when both are in.
Role change / deactivateTwo case actions that already exist elsewhere (role on the profile; deactivate + void PIN + reassign). The case item just calls them and records who.

Build order: migration (three tables, bucket, RLS, grants) → lib/hrChecklists.ts + the case page with a working checklist (you can use it for Quinn's promotion the same day, ticking the document rows by hand) → documents: form, render, send, sign, PDF, auto-tick. Two sessions. The HR-SPEC's template engine isn't built and doesn't need to be — if a checklist ever needs to change, it's a code edit; live cases keep their copy.

6Rulings I need from you

  1. Vacation. What's the annual number at full time, and does it scale with days/week (a 3-day person gets 3/5 of it)? The form assumes yes. And is it days or hours?
  2. Who sees pay. Fernando runs the checklist but you set pay. Can he see the rate on the case (simplest — he's uploading the signed letter to ADP anyway), or is the offer letter form owner-only?
  3. Signing an existing employee. For a promotion, the letter goes to their personal email like a new hire, or do you want it to also appear in-app on their dashboard ("You have a document to sign")? I'd ship email-only first.
  4. Job descriptions. Do you have written JDs for the roles beyond the 2025 Billing Coordinator one? If not, the first JD you send for each title becomes the seed and I draft Studio Manager from what you tell me.
  5. Letter signer. Every letter signs as you, or can Fernando send a letter as himself?
  6. New hire day one. "PRSFlo staff record + PIN" as a case action creates the profile and runs set-pins.mjs --only's logic in-app — or keep that a manual step you do from the terminal like today?
